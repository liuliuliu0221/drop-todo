# M4：稳定性与内测分发

## 1. 阶段目标

把功能完整版本提升到可以交给不同 macOS 13+ 刘海 Mac 用户连续使用的质量，并建立可重复的手动发布流程。M4 不新增产品功能。

## 2. 冻结规则

进入 M4 后执行功能冻结：

- 只接受 P0/P1 修复、明确的 P2 修复和发布阻断项；
- 视觉优化不得改变已确认交互；
- Schema 变化必须有迁移测试；
- 依赖升级必须与功能改动分开；
- 不临时加入 Sparkle、通知、遥测或多显示器渲染。

## 3. M4A：自动化质量门禁

每个候选构建必须运行：

```bash
xcodebuild \
  -project WaterDropTodo.xcodeproj \
  -scheme WaterDropTodo \
  -configuration Release \
  -destination 'platform=macOS' \
  test
```

门禁包括：

- 全部单元和集成测试通过；
- `WaterDropTodo`、`WaterDropTodoTests`、`WaterDropTodoUITests` 三个 Target 均可构建，Swift Testing 与 XCTest 职责符合工程基线；
- Release 编译无新增警告；
- Swift 6 Strict Concurrency `Complete` 下并发诊断为零；
- Thread Sanitizer 专项构建通过核心业务测试；
- Address Sanitizer 专项构建完成窗口和动画循环测试；
- 数据 Fixture 覆盖当前 Schema、备份恢复和迁移失败；
- `git diff --check` 和资源引用检查通过；
- Release 构建不包含 Debug 面板和可识别任务日志。

Sanitizer 构建不作为最终签名包，但结果必须存档。

2026-08-21 的 M4A 实现与验证结果见 [M4A 验证记录](./M4A_验证记录_2026-08-21.md)。M4B 性能兼容和 M4C 分发内测仍按后续章节执行。

## 4. M4B：性能与能耗

基准场景：8 个 active 水滴、鱼缸显示、无用户交互，连续 30 分钟。

| 指标 | 门槛 |
|---|---|
| 已运行应用按 `⌥T` 到可输入 | P95 ≤ 300ms |
| 稳态平均 CPU | 基准机 ≤ 2% |
| 30 分钟稳态内存 | ≤ 150MB 且无持续增长 |
| 唤醒后状态校正 | ≤ 1 秒 |
| 短动画 | 无明显掉帧，目标接近屏幕刷新率 |
| 点击穿透 | 无可感知延迟和系统菜单误拦截 |

使用 Instruments 的 Time Profiler、Allocations、Leaks 和可用的能耗模板。Xcode 26 在 macOS 上不支持 Power Profiler 且不再提供 Energy Log 时，记录该工具限制并使用 Activity Monitor trace 与长时间 CPU/内存采样替代。所有结果记录构建号、机型、系统版本和测试数据量。

2026-08-21 的 M4B 自动化实现、当前基准机结果和未验证兼容性矩阵见 [M4B 验证记录](./M4B_验证记录_2026-08-21.md)。当前单机性能和可靠性门禁已通过，但跨版本、跨设备及三人 7 天证据尚未完成。

## 5. M4B：可靠性与破坏性测试

- 100 次创建、编辑、完成、取消、逾期和召回混合操作；
- 20 次不同写入时机的强制退出与重启；
- 主文件截断、非法 JSON、previous 有效和双文件损坏；
- 写入权限失败、磁盘空间不足的模拟；
- 动画中退出、睡眠和屏幕配置变化；
- 快捷键冲突和重新录制；
- 完成、焚毁和清除操作快速重复点击；
- 跨日、跨月、跨年、时区变化和系统时间回拨；
- 覆盖安装新构建后数据保留。

双文件均损坏时不得静默创建空库覆盖原文件；应保留文件、提示用户并提供导出诊断入口。

## 6. M4B：兼容性矩阵

内测登记收集：机型、屏幕尺寸、芯片、macOS 版本、是否常用外接屏。

最低覆盖：

- arm64、带内置刘海的 Apple Silicon Mac，macOS 13.x 至少一台；
- 测试池可获得的后续主要 macOS 版本；
- 至少两种刘海屏幕尺寸；
- Safari 全屏视频、Keynote、Xcode、Finder 和一种游戏或高刷新窗口；
- 单屏、外接显示器、镜像、睡眠唤醒、Reduce Motion；
- 至少三名用户连续使用 7 天。
- 无刘海设备验证启动阻断提示与安全退出；
- 外接显示器、镜像和合盖仅使用外接屏验证刘海能力暂停、主应用继续运行及恢复策略。

没有实机证据的版本标记“未验证”，不写成已兼容。若某一系统版本存在 P1 且无法在本阶段修复，应调整支持声明，不得带病放行。

## 7. M4C：签名、公证和 DMG

### 7.1 前置资产

- Apple Developer Program 团队；
- Developer ID Application 证书；
- 稳定 Bundle ID；
- 应用名称、图标和版本号；
- CI 或发布机上的安全证书存储；
- 隐私说明和内测反馈渠道。

证书、私钥、notary 凭据和临时 keychain 不得提交仓库。

### 7.2 发布流水线

1. 从干净工作区构建 Release Archive；
2. 使用 Developer ID 导出并验证签名；
3. 生成带 `/Applications` 快捷方式的 DMG；
4. 提交 Apple notary service；
5. notarization 成功后 staple；
6. 使用 `codesign --verify`、`spctl` 和 `stapler validate` 验证；
7. 在未安装开发证书的干净账户上安装和启动；
8. 计算 SHA-256；
9. 上传内测下载位置并发布变更说明；
10. 保存构建号、Commit、校验值和公证结果。

POC/MVP 使用手动覆盖安装，不包含 Sparkle。每个内测版本仍必须递增 `CFBundleVersion`，并验证 Application Support 数据不受覆盖安装影响。

2026-08-21 的无证书发布基础设施、dry-run 结果和剩余签名阻塞见 [M4C 验证记录](./M4C_验证记录_2026-08-21.md)。dry-run 产物使用 ad-hoc 签名，只能验证流水线，不能替代 Developer ID 签名和 Apple 公证。

## 8. M4C：内测运行

每个问题至少记录：

- 构建号；
- 机型和 macOS；
- 是否外接屏或全屏；
- 复现步骤；
- 期望和实际结果；
- 是否涉及数据错误；
- 用户主动导出的诊断包。

不得要求用户直接发送包含私人任务标题的完整数据文件；只有定位数据一致性问题且用户明确同意时才使用任务导出。

## 9. M4C：缺陷放行

| 等级 | 示例 | 放行规则 |
|---|---|---|
| P0 | 数据丢失、无法启动、签名安全问题 | 必须为 0 |
| P1 | 核心闭环阻断、时间/状态错误、主要机型不可用 | 必须为 0 |
| P2 | 有绕过方式的交互、局部布局或动画问题 | 有负责人和计划，逐项评审 |
| P3 | 文案、低频视觉细节 | 可进入后续迭代 |

## 10. M4C：发布检查清单

- [ ] 功能冻结后没有未审查范围变化；
- [ ] 自动化、Sanitizer 和数据破坏测试通过；
- [ ] 性能、内存和能耗达到门槛；
- [ ] 兼容性矩阵完成并记录未验证项；
- [ ] P0/P1 为 0；
- [ ] 版本号、Bundle ID、图标和隐私说明正确；
- [ ] Developer ID 签名有效；
- [ ] 公证成功并 staple；
- [ ] DMG 在干净账户可安装；
- [ ] SHA-256 和变更说明已生成；
- [ ] 覆盖安装保留任务数据；
- [ ] 反馈渠道和诊断导出说明可用；
- [ ] 至少三名用户完成 7 天试用。

## 11. M4C：MVP 退出条件

- POC 文档全部必须项完成；
- 第 10 节发布清单通过；
- 内测期间没有未解决的数据丢失或时间错误；
- 多数内测用户能独立完成创建、查看、完成、逾期和召回；
- 多数用户愿意继续让应用常驻下一周；
- 已记录核心产品假设的正反反馈，能够决定进入视觉精修、继续迭代或调整方向。
