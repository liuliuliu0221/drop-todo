# MVP 总体架构与工程规范

## 1. 架构目标

MVP 架构优先保证四件事：

1. 截止时间和任务状态在重启、睡眠及系统时间变化后仍然正确；
2. 刘海渲染、鼠标命中和业务状态相互解耦；
3. 动画失败或中断不能反向破坏已持久化的任务状态；
4. 常驻应用按需刷新，不用持续 60fps 换取简单实现。

采用“领域核心 + 平台适配 + 功能模块”的分层结构。SwiftUI View 不直接写文件、不直接改变任务状态，也不拥有窗口生命周期。

启动时使用 `NSScreen.safeAreaInsets` 与 auxiliary areas 检测内置刘海：无刘海时显示“不支持此设备”并退出；任意外接显示器、镜像或合盖仅使用外接屏时暂停刘海相关窗口，但应用和任务状态继续运行。`NSPrefersDisplaySafeAreaCompatibilityMode = false` 只有在 M0 真机审计通过后才固定到 Release 配置。

### 3.1 为什么拆分渲染窗口和命中窗口

透明但可接收鼠标的矩形窗口可能拦截下层菜单栏操作。MVP 不依赖“透明像素天然点击穿透”的假设：

- `NotchRenderPanel` 只负责 Metal 渲染，始终 `ignoresMouseEvents = true`；
- 每个可见任务使用一个小型 `DropletHitPanel` 覆盖扩大命中区；
- `HoverCardPanel` 承担卡片按钮与透明交互走廊；
- `HitTestCoordinator` 根据同一份布局快照更新渲染与命中坐标。

这样只有水滴和卡片附近的小区域可能拦截鼠标，刘海周围其余透明区域始终穿透。

## 4. 领域模型

```swift
enum TaskStatus: String, Codable, Sendable {
    case active
    case ruined
    case completed
    case recalled
}

enum Urgency: Int, Codable, Sendable {
    case low
    case medium
    case high
}

enum TaskTag: String, Codable, Sendable {
    case work
    case life
    case inspiration
}

struct TaskRecord: Codable, Identifiable, Sendable {
    let id: UUID
    var title: String
    var deadline: Date
    var tag: TaskTag?
    var urgency: Urgency
    var status: TaskStatus
    var createdAt: Date
    var visualStartAt: Date
    var completedAt: Date?
    var ruinedAt: Date?
    var recalledAt: Date?
    var recalledFromID: UUID?
}
```

取消和焚毁是删除命令，不增加持久状态。`hovered`、`pinned`、`completing`、`falling`、`cracking` 是会话内展示状态，不写入 TaskRecord。

## 5. 领域服务接口

所有改变任务的入口都通过 `TaskService`：

```swift
protocol TaskServicing: Sendable {
    func create(_ input: CreateTaskInput) async throws -> TaskRecord
    func update(id: UUID, changes: TaskChanges) async throws
    func complete(id: UUID, at: Date) async throws -> CompletionSnapshot
    func cancel(id: UUID) async throws
    func expireDueTasks(at: Date) async throws -> [ExpirationSnapshot]
    func recall(id: UUID, newDeadline: Date, at: Date) async throws -> TaskRecord
    func burn(id: UUID) async throws
    func clearCompleted() async throws
}
```

动画只消费 `CompletionSnapshot` 或 `ExpirationSnapshot`，不在动画结束回调中才提交领域状态。由此保证动画中断后数据仍然正确。

## 6. 持久化

### 6.1 文件

```text
FileManager.applicationSupportDirectory
└── WaterDropTodo/
├── tasks.json
├── tasks.previous.json
└── Logs/
```

应用保持沙盒，禁止硬编码非沙盒绝对路径。实际路径由 `FileManager` 在当前容器内解析；导出数据和日志时通过 `NSSavePanel` 获取用户授权的读写位置。

数据封装：

```swift
struct StoreEnvelope: Codable {
    let schemaVersion: Int
    let savedAt: Date
    var tasks: [TaskRecord]
}
```

### 6.2 写入流程

1. `TaskStore` actor 接收变更；
2. 在内存副本上验证不变量；
3. 编码新 Envelope；
4. 将当前有效文件复制为 previous；
5. 以临时文件和原子替换写入主文件；
6. 成功后发布新的只读快照；
7. 失败时保留原内存和磁盘状态并抛出错误。

不得在主线程执行文件编码和写入。迁移失败时保留原文件，不得用空数组覆盖。

## 7. 时间模型

- 截止时间使用绝对 `Date`；
- UI 展示使用用户当前 Calendar、Locale 和 TimeZone；
- 任务状态不依赖 Timer 累加；
- `TimeEngine` 计算下一截止点并安排一次性调度；
- 倒计时刷新和领域到期调度分开；
- 悬停 60 秒保护使用单调时钟，避免系统时钟调整改变保护时长；
- 启动、唤醒、重新激活、系统时间或时区变化时调用 `reconcile(now:)`。

测试必须使用可注入 `Clock`/`NowProvider`，禁止在领域测试中直接调用 `Date()`。

## 8. 液体渲染

### 8.1 Metal 基线

- 使用透明 `MTKView`；
- fragment shader 接收液面和最多 8 个水滴的统一参数；
- 使用 metaball 场或等价连续隐式面计算连接轮廓；
- 颜色由 `visualProgress` 插值；
- 沥青感通过颜色、边缘和低频扰动实现，先保证形态再追求材质；
- CPU 布局输出同时供 shader 与命中窗口使用。

### 8.2 刷新策略

- 稳态时间位置低频更新；
- 低频液体微动限制在约 8～12fps；
- 悬停、坠落、完成等短动画按屏幕刷新率运行；
- 无可见水滴时暂停 MTKView；
- `enableSetNeedsDisplay` 和 `isPaused` 由渲染状态机控制；
- 不允许任务存在时无条件永久 60fps。

## 9. 坐标系统

窗口和动画统一使用 AppKit 全局屏幕坐标。每次动画开始时创建不可变 `TransitionGeometry`：

```text
sourceRectInScreen
targetPointInScreen
screenFrame
backingScaleFactor
```

SwiftUI 局部坐标必须先转换到窗口坐标，再用 `convertToScreen` 转为全局坐标。动画进行中屏幕结构变化时取消视觉动画，但不回滚已提交的业务状态。

## 10. 并发与线程

- 全工程使用 Swift 6 且 Strict Concurrency 为 `Complete`；
- 不启用全局默认 MainActor，隔离必须在类型和接口上明确表达；
- AppKit/SwiftUI 状态和窗口对象固定在 `@MainActor`；
- `TaskStore` 使用 actor；
- 文件编码、日志压缩等工作离开主线程；
- 领域模型、动画快照和 Metal 参数快照为 `Sendable` 值类型，通过明确同步点交给消费者；
- 禁止多个 ViewModel 各自修改同一任务数组；
- 所有异步任务持有者都要定义取消时机，窗口关闭和应用退出不得遗留循环任务。

## 11. 依赖策略

MVP 只引入解决明确平台缺口的依赖：

| 依赖 | 用途 | 策略 |
|---|---|---|
| KeyboardShortcuts 3.0.1 | 全局快捷键和录制 UI | SPM 精确锁定版本，M1 引入 |

开机启动优先直接使用 macOS 13 的 `SMAppService`；设置使用自有类型安全封装；POC/MVP 不引入 Sparkle、Lottie、第三方日期解析和第三方流体渲染库。

所有依赖必须通过 SPM，提交 `Package.resolved`。依赖升级必须独立提交，并重新验证 Debug、Release 和测试构建。

## 12. 测试架构

`WaterDropTodoTests` 以 Swift Testing 编写单元与集成测试；需要 `XCTMetric` 的性能测试可在同一 Target 使用 XCTest，但单个测试不得混用两套断言 API。`WaterDropTodoUITests` 使用 XCTest/XCUIAutomation。

### 12.1 单元测试

- TaskService 所有命令和非法状态；
- 时间进度、紧急度偏移和边界；
- 快捷时间选项跨日行为；
- 到期、召回和删除关联；
- Schema 编解码、迁移和恢复；
- 8 水滴布局、最小间距和稳定性。

### 12.2 集成测试

- TaskService + TaskStore 真临时目录；
- TimeEngine + 虚拟时钟；
- WindowCoordinator 生命周期；
- 全局坐标转换；
- 睡眠/时间变化通知后的 reconcile。

### 12.3 UI 与实机测试

UI 测试覆盖创建、编辑、完成、取消、废墟、召回和设置。Metal、点击穿透、全屏层级、触觉和窗口焦点必须保留实机清单，不能假设 UI 自动化能够完全覆盖。

## 13. 日志与错误

- 使用 `Logger`/OSLog 分类：app、store、time、window、render、animation；
- 默认日志不记录任务名称；
- 用户可见错误使用明确中文，不暴露内部路径或堆栈；
- 数据恢复、快捷键冲突、窗口创建失败和公证版本信息必须可诊断；
- 日志保留 7 天，只有用户主动导出后才离开设备。

## 14. 安全与隐私

- 保持 App Sandbox 启用；
- 用户选择文件 entitlement 使用读写，只在明确的导出操作中获取访问；
- 不请求非必要辅助功能、输入监控、屏幕录制或通知权限；
- 不使用私有 API；
- 不自动联网；
- Developer ID、notary 和更新签名密钥不得提交仓库；
- 导出文件由用户显式选择位置；
- 任何未来网络能力都必须先更新隐私说明和 ADR。
